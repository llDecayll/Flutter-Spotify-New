# Time Machine — the timeline-AR core

This is a runnable slice of the scenario: *nearby-monument alert → world map →
open a monument → scrub its timeline (including "not built yet") → 3D
reconstruction changes per era with voice narration → look around by moving the
phone, monument stays anchored.*

Open `/time.html` (linked from the main start screen). Try it with `?live=1` to
use real GPS; otherwise a position ~2.6 km from the Taj Mahal is simulated so
the nearby-alert flow works anywhere.

## What is real in this prototype

- **Geofenced "nearby" alert** — distance from your position to each registered
  monument; fires an in-app card and a Web Notification (if permitted).
- **World map** with blinking, tappable markers (offline projection, no tiles).
- **Timeline scrubber** across eras, including an **`absent`** state so "in 900
  BCE the Taj Mahal wasn't here — just the riverbank" is shown literally: the
  3D monument is removed and only the site remains.
- **3D reconstruction** rendered with Three.js (WebGL). The monument is
  **world-anchored**: the camera is fixed and you rotate to look around it
  (device orientation on a phone, drag on desktop). Verified end-to-end,
  including that the rendered frame genuinely differs between eras.
- **Per-era voice narration** generated by **Claude Fable 5** (`/api/timeline`),
  with the site notes as an offline fallback.
- **Upload pipeline** (`POST /api/monuments`) — the "someone scanned and
  uploaded a monument" step: register a monument with a per-era timeline and a
  `modelUrl` (glTF/GLB) for each era. It immediately appears on the map for
  everyone.

## What is a stand-in / not real yet — and why

| Your scenario | Status here | What it really needs |
|---|---|---|
| 3D model = a real photogrammetry scan someone uploaded | ❌ Procedural Taj Mahal built from primitives | A `GLTFLoader` on the per-era `modelUrl` (same code path); real capture is a content-production effort |
| Walk *inside/around* and the AR stays locked as you move (6DoF) | ❌ 3DoF only — you rotate, you don't translate | Native ARKit/ARCore + a VPS (ARCore Geospatial API / Lightship) for world-scale positional anchoring. Not possible in a mobile browser. |
| Alert while the app is **closed / backgrounded** | 🟡 Foreground + Web Notification only | Native background geofencing + push (iOS/Android). Web can't run geofences when the tab is closed. |
| Turn-by-turn navigation to the site | ❌ Distance/marker only | Deep-link to native maps, or a routing SDK |

The two hard ones — **real uploaded 3D meshes** and **6DoF VPS anchoring** — are
exactly the "expensive core" flagged throughout: they need a native Unity/AR
client and a content pipeline, not a web prototype. What this build proves is
the whole experience *around* the mesh (discovery → map → timeline → narration →
anchored look-around → upload), so that when the native 3D layer is dropped in,
everything it plugs into already exists and is tested.

## Swapping in a real scanned model

`timemachine.js` builds the monument procedurally in `_tajMahal()`. To use a
real scan, load the era's `modelUrl` instead:

```js
import { GLTFLoader } from "/vendor/GLTFLoader.js";
// in setEra(): if (era.modelUrl) new GLTFLoader().load(era.modelUrl, gltf => group.add(gltf.scene));
```

The registry, map, timeline UI, narration, and look-around stay unchanged.

## Battery / thermal

The 3D view uses **render-on-demand**: it only draws a frame when the camera
moves or the era changes, so holding still idles the GPU. Rendering also stops
when the tab is hidden. (See the main README's thermal section for the AR-guide
render loop.)
